# Task 7: aichat Tool Schema Generation Code Analysis

## Summary

This document traces the complete pipeline from tool source definitions through to the JSON schema sent to OpenAI's API, focusing on how `required` arrays are populated and why the generated schemas violate strict mode requirements.

## Schema Generation Pipeline

### Stage 1: Tool Source Files (`llm-functions/tools/`)

Tools are defined as shell scripts (`.sh`), Python files (`.py`), or JavaScript files (`.js`). Each language uses its own convention to declare parameters and their optionality.

**Location**: `/home/pdibiase/sources/llm-functions/tools/`

### Stage 2: Build Declarations Scripts (`llm-functions/scripts/build-declarations.{sh|py|js}`)

These scripts parse tool source files and generate JSON schema declarations.

#### Shell (`build-declarations.sh`)
Uses `argc --argc-export` to get structured flag/option metadata, then processes with `jq`:
```jq
required: [flag_options[] | select(.required == true) | .id | sub("-"; "_"; "g")]
```
- `@option --name!` → `.required == true` → included in `required` array
- `@option --name` → `.required == false` → NOT included
- `@flag --name` → never required (flags are always optional)

#### Python (`build-declarations.py`)
Reads AST annotations:
```python
if type_.endswith("?"):  # comes from Optional[T] annotation
    type_ = type_[:-1]
    required = False
```
- `param: str` → required
- `param: Optional[str]` → optional (becomes `"str?"` internally)
- Only required params are added to `required_params` list

#### JavaScript (`build-declarations.js`)
Reads JSDoc `@property` annotations:
```javascript
if (/^\[.*\]$/.test(name)) {
    name = name.slice(1, -1);
    required = false;
}
```
- `@property {type} name` → required
- `@property {type} [name]` → optional (brackets = optional)

### Stage 3: `functions.json` Output

The build scripts output a JSON array of declarations. Example structure:
```json
{
  "name": "recursive_grep",
  "description": "Search files recursively for a specific pattern.",
  "parameters": {
    "type": "object",
    "properties": {
      "pattern": {"type": "string", "description": "..."},
      "directory": {"type": "string", "description": "..."},
      "file_pattern": {"type": "string", "description": "..."},
      "ignore_case": {"type": "boolean", "description": "..."},
      ...
    },
    "required": ["pattern", "directory"]
  }
}
```

**Critical observation**: Only genuinely required parameters are in `required`. No `additionalProperties` field is generated by any build script.

### Stage 4: aichat Loads `functions.json`

**File**: `src/config/mod.rs:60` defines `FUNCTIONS_FILE_NAME = "functions.json"`
**File**: `src/function.rs:74-96` — `Functions::init()` loads and deserializes:
```rust
let content = fs::read_to_string(declarations_path).with_context(ctx)?;
match jsonic::parse(&content) {
    Ok(json_item) => {
        let json_str = json_item.as_str().unwrap_or_default();
        serde_json::from_str(json_str).with_context(ctx)?
    }
    ...
}
```

Deserialized into:
```rust
pub struct FunctionDeclaration {     // function.rs:118-124
    pub name: String,
    pub description: String,
    pub parameters: JsonSchema,
    #[serde(skip_serializing, default)]
    pub agent: bool,
}

pub struct JsonSchema {              // function.rs:126-149
    pub type_value: Option<String>,         // "type" field
    pub description: Option<String>,
    pub properties: Option<IndexMap<String, JsonSchema>>,
    pub items: Option<Box<JsonSchema>>,
    pub any_of: Option<Vec<JsonSchema>>,
    pub enum_value: Option<Vec<String>>,    // "enum" field
    pub default: Option<Value>,
    pub required: Option<Vec<String>>,
}
```

**CRITICAL GAP**: `JsonSchema` has NO `additionalProperties` field. Even if `functions.json` contained it, aichat would silently drop it during deserialization.

**None of these add `additionalProperties: false` or modify the `required` array.**

## Strict Mode Compliance Analysis

### What Strict Mode Requires (OpenAI)
1. `additionalProperties: false` on EVERY object in the schema
2. ALL properties must be in the `required` array
3. Optional parameters must use nullable type: `{"type": ["string", "null"]}`

### Where aichat Fails

| Requirement | Status | Root Cause |
|-------------|--------|------------|
| `additionalProperties: false` | ❌ NEVER set | `JsonSchema` struct has no field for it; build scripts don't generate it |
| All props in `required` | ❌ Only truly required params included | Build scripts correctly distinguish required/optional by language convention |
| Nullable types for optional | ❌ Not implemented | Build scripts use standard JSON Schema types without null unions |
| `strict: true` field | ❌ Never explicitly set | aichat relies on Responses API auto-normalization |

### Concrete Examples from Generated `functions.json`

**fs_git_diff** (worst case — 2 properties, 0 required):
```json
{
  "required": [],
  "properties": {"path": {...}, "cached": {...}}
}
```
→ Strict mode needs: `"required": ["path", "cached"]` + `"additionalProperties": false`

**recursive_grep** (7 of 9 properties missing from required):
```json
{
  "required": ["pattern", "directory"],
  "properties": {"pattern": {...}, "directory": {...}, "file_pattern": {...}, ...7 more}
}
```
→ Strict mode needs ALL 9 in required + `"additionalProperties": false`

**patch** (compliant on required — all 11 listed):
```json
{
  "required": ["path", "contents", "dry_run", "atomic", "verbose", ...all 11],
  "properties": {...all 11 properties}
}
```
→ Still missing `"additionalProperties": false` but required array IS complete

## Fix Points (Where Changes Could Be Made)

### Option A: Fix at build-declarations time (llm-functions project)
- Modify `build-declarations.{sh|py|js}` to always add ALL properties to `required`
- Add `"additionalProperties": false` to the parameters object
- Change optional params to use nullable types: `{"type": ["string", "null"]}`
- **Pro**: Fix at source, affects all consumers of functions.json
- **Con**: Breaks semantics — LLMs should know which params are optional

### Option B: Fix at aichat serialization time (aichat project)
- Add `additionalProperties` field to `JsonSchema` struct (function.rs)
- When serializing for Responses API, dynamically:
  - Add all properties to `required`
  - Set `additionalProperties: false` on all objects
  - Convert optional params to nullable: `{"anyOf": [{"type": "string"}, {"type": "null"}]}`
- **Pro**: Only affects strict-mode-requiring backends; preserves semantic accuracy in functions.json
- **Con**: Requires model/backend detection logic

### Option C: Set `strict: false` explicitly in API request
- Add `"strict": false` to each tool definition in the Responses API body
- **Pro**: Simplest one-line fix; no schema changes needed
- **Con**: May not override Responses API auto-normalization; model may still behave strictly

### Option D: Reduce tool count below soft limit
- Send fewer than 20 tools per request for GPT-5.5
- **Pro**: Addresses tool count soft limit
- **Con**: Doesn't fix the schema compliance issue; just reduces probability of failure

## Conclusion

The schema generation pipeline was designed for the pre-strict-mode era of OpenAI's API. It correctly distinguishes between required and optional parameters at the semantic level, but this distinction is INCOMPATIBLE with OpenAI's strict mode requirements (which demand ALL properties in `required`). Combined with the complete absence of `additionalProperties: false` anywhere in the pipeline and the Responses API's automatic strict normalization, this creates schemas that GPT-5.5 cannot comply with — resulting in the observed 0-token "completed" response.
